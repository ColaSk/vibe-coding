## 1 核心结论速览

数仓建模要先分清「分层、星型、历史」三套决策，再按业务过程声明粒度。

| 编号 | 结论 | 信心 |
|------|------|------|
| 1 | 数仓建模的核心不是「把表分分层」，而是把可观察的业务事件拆成**度量（事实）**和**描述上下文（维度）**，再放到可复用的层里 | 高 |
| 2 | 设计时只反复问四件事：**业务过程、粒度、维度、事实**（Kimball 四步） | 高 |
| 3 | **分层、星型/雪花、SCD** 是三套正交决策：货架、摆法、时间旅行规则。有拉链表不等于已经维度建模 | 高 |
| 4 | 当代常见组合是：贴源保真，集成层用 3NF 或 Data Vault 管历史，消费层用 Kimball 星型给报表。Lakehouse 的 Bronze/Silver/Gold 是同一精炼链的另一套名字 | 高 |
| 5 | 事实表外键应指向仓库 **代理键**，而不是源系统自然键；否则 SCD2 无法让历史事实钉在「当时」那一版维度上 | 高 |
| 6 | 国内 ODS/DIM/DWD/DWS/ADS 与 Medallion 的对应是**职责近似、并非一一物理等同**；各厂对 DWD 是否「轻度汇总」存在用词分歧 | 中 |

## 2 概述：数仓建模解决什么

源系统是 **OLTP**（Online Transaction Processing）：要写得快、约束强，模型通常第三范式（3NF）。数仓面向 **OLAP**（Online Analytical Processing）：要按「谁、什么、何时、多少」切片汇总。

Kimball 把分析世界分成两类东西（S1、S2）：

- **事实（fact）**：业务过程产生的、几乎总是数值的度量。一行事实对应一次可观察的度量事件。
- **维度（dimension）**：围绕该事件的 who / what / where / when / why / how。维表提供筛选和分组入口。

因此数仓建模的工作，是把经营里反复发生的事件，变成：**一张（或一组）粒度明确的事实表 + 一组可治理的维度表**，再按加工深度放到不同层，避免每个报表私自定义口径。

**信心：高。** S1 与 S2 对事实/维度的定义一致；S3/S4 把同一套思想落到 DWD 事实表设计步骤上。

## 3 先分清三件常被混在一起的事

| 层次 | 解决什么 | 典型名词 |
|------|----------|----------|
| 存储与加工位置 | 数据放哪一层、何时清洗聚合 | ODS / DWD / DWS / ADS，Bronze / Silver / Gold |
| 表怎么关联 | 分析时怎么 Join、怎么切片 | 星型、雪花、总线、Hub-Link-Satellite |
| 历史怎么记 | 属性变了，旧事实跟哪一版走 | SCD、拉链、代理键、Satellite |

宽表化是物理加速（少 Join），不是分层替代品，也不是粒度声明。没有粒度的宽表只是报表缓存。

相邻概念，避免串台：

| 词 | 不是什么 |
|----|----------|
| OLTP | 不是数仓。高并发事务库 |
| OLAP | 分析查询形态：可以是星型 SQL，也可以是 Cube |
| 数据集市 Data mart | 面向主题的消费集，不是整个企业仓 |
| 数据湖 / Lakehouse | 存储形态。湖可以无模型；仓必须有模型。Lakehouse 把二者叠在同一套表格式上 |
| ETL / ELT | 加工发生在仓外还是仓内。现代仓多为 ELT：先载入再变换 |
| 规范化 3NF | OLTP 和 Inmon 核常用。维度建模故意反规范化维表 |

**信心：高。** 分层与建模手法的区分在 S3 与 S2 中都能独立读到；「宽表不等于模型」是实践推论，与 S4「可适当冗余」一致。

## 4 三大方法论

数据从源系统进来，先进入企业集成层（Inmon 的 3NF 核，或 Data Vault），再投影到分析消费层（Kimball 星型 / ADS / Gold）。

今天很少只选一家。常见组合是：贴源/原始层保真，集成层管历史与变更，消费层给报表星型（S5、S6、S7）。

### 4.1 Kimball（自底向上）

按业务过程建 **星型（star schema）**：中央事实表通过外键连接多张扁平维表。多个过程靠 **一致性维度（conformed dimension）** 钉在同一套客户/商品/日期上，形成 **总线架构（bus architecture）**。规划工具是 **总线矩阵（bus matrix）**：行是业务过程，列是一致性维度。

出数快，适合分析团队。企业一致性靠总线约束，而不是先建一张巨大企业核。

### 4.2 Inmon CIF（自顶向下）

先建企业级规范化 EDW（通常 3NF），再派生数据集市。口径统一成本前置，周期长，适合监管强、主题多、要「单一真相」的组织（S5、S6）。

### 4.3 Data Vault 2.0（集成优先）

把实体拆成三类对象，便于源系统变更和全量溯源（S6、S7）：

| 构件 | 存什么 | 不存什么 |
|------|--------|----------|
| Hub | 业务实体的稳定业务键 + 加载元数据 | 描述属性 |
| Link | 两个或多个 Hub 之间的关系 | 关系上的描述细节 |
| Satellite | 挂在 Hub 或 Link 上的描述属性，按时间片保存 | 业务键本身 |

Hash key 由业务键算出，方便并行加载。PIT（Point-in-Time）和 Bridge 属于 Business Vault 的查询辅助。给人看的报表仍要再做成 **Information Mart / 星型**。

Data Vault 不是和 Medallion 互斥：实践上常把 Raw Vault 放在 Silver，星型放在 Gold（S7）。

**信心：高**（三套方法各自的定义）；**中**（「当代默认混合」——厂商实践文一致，但不是 ISO 级标准）。

## 5 分层：国内五层与 Lakehouse 三层

阿里云 DataWorks 默认五层，并把表挂到「贴源 / 公共 / 应用」三档归属（S3）：

| 层 | 全称 | 职责 | 大约对应 |
|----|------|------|----------|
| ODS | Operational Data Store | 贴源落地，结构靠近源系统；增量/全量同步，日志结构化 | Bronze / Staging |
| DIM | Dimension | 企业一致性维表：主键、属性、层级、缓慢变化 | Silver 公共维 / Gold 维表 |
| DWD | Data Warehouse Detail | 按业务过程建最细粒度明细事实，可轻度宽表化 | Silver 明细 / atomic fact |
| DWS | Data Warehouse Summary | 按主题对象做公共粒度汇总 | Gold 汇总 / aggregate fact |
| ADS | Application Data Service | 面向具体产品或报表的个性化指标与宽表 | Gold mart / serving |

DataWorks 推荐表名前缀（S3）：

- DIM：`dim_业务分类_数据域_自定义_存储策略`
- DWD：`dwd_业务分类_数据域_业务过程_自定义_存储策略`
- DWS：`dws_业务分类_数据域_自定义_时间周期`
- ADS：`ads_业务分类_数据集市_主题域_自定义_时间周期`

公共层还会用到：

| 名词 | 含义 |
|------|------|
| 数据域 | 相对稳定的业务分析范围，如交易、流量、用户。用来切公共层，不是按报表切 |
| 业务过程 | 可观测的经营活动，如下单、支付。DWD 事实表按过程建 |
| 数据集市 | 面向部门或产品的消费集合，挂在应用层 |
| 主题域 | 应用层里按分析主题再切，如 GMV、留存 |

**用词分歧（已标注）**：S3 写 DWD 是「最细粒度明细」；部分阿里云开发者文章把 DWD 写成「基于 ODS 和 DIM 做轻度汇总」。本文以产品文档 S3/S4 为准：DWD = 明细事实，汇总放到 DWS。社区文章的「轻度汇总」视为口语混用。

**信心：高**（五层职责以 S3 为准）；**中**（与 Bronze/Silver/Gold 的列级映射——职责近似，物理落点因团队而异）。

## 6 维度建模四步

Kimball 四步必须按序，且必须同时看业务需求和源数据现实（S2）。S4 把同一四步用于 DWD 明细事实表。

1. **选业务过程**：测的是哪类经营活动：下单、支付、发货，还是每月账户快照。一张事实表对应一个过程，不要按报表倒推表。
2. **声明粒度**：一行事实究竟代表什么。粒度是合同；不同粒度不能混在同一张事实表。优先原子粒度（过程捕获的最低层），汇总是性能优化，不能替代原子层。
3. **识别维度**：围绕该事件、且对该事实行单值的上下文。
4. **识别事实**：只放与粒度一致的数字。零售订单行可以有数量和金额，不能塞店长工资。

星型关系可以记成：事实表「订单行」分别连日期维、客户维、商品维、门店维。

- **星型**：事实表直接连多张扁平维表，查询简单，是关系库上的默认形态。
- **雪花（snowflake）**：维表再规范化出层级子表，冗余少、Join 多。Kimball 默认扁平星型；雪花只在工具或层级必须独立维护时用。Outrigger 是只雪花一小块的折中。
- **OLAP Cube**：同一套维度内容的多维实现，常作为星型之上的聚合部署（S2）。

**信心：高。**

## 7 事实表

事实表又瘦又长：外键 + 可选退化维 + 数值度量。设计跟着真实发生的事件走，不跟着某张报表走（S1、S2）。

### 7.1 三种基础事实表

| 类型 | 一行代表 | 典型问题 | 更新方式 |
|------|----------|----------|----------|
| 事务事实 Transaction | 一次发生：一笔订单行、一次支付 | 卖了多少、退了多少 | 通常只追加 |
| 周期快照 Periodic snapshot | 固定周期末的状态：日库存、月账户余额 | 现在还剩多少 | 每个周期插入一张快照 |
| 累积快照 Accumulating snapshot | 一条管全程：订单从下单到签收 | 履约时效、卡在哪一步 | 同一行随里程碑被更新 |

S4 对 DWD 三种事实表的分类与 S2 一致。

### 7.2 可加性

| 类别 | 规则 | 例子 |
|------|------|------|
| 完全可加 Additive | 沿所有维度都能 SUM | 销售额、件数 |
| 半可加 Semi-additive | 某些维度可加，时间通常不可加 | 账户余额、库存数量 |
| 不可加 Non-additive | 不能直接 SUM；先存分子分母再算 | 利润率、单价、占比 |

### 7.3 其他高频事实名词

| 名词 | 一句话 |
|------|--------|
| 无事实事实表 Factless | 只记录事件发生，没有度量列。如学生出勤、促销覆盖 |
| 退化维度 Degenerate | 没有独立维表的维度值，如订单号，留在事实表里 |
| 一致性事实 Conformed fact | 跨过程同名度量必须同单位、同算法，才能钻取对比 |
| 聚合事实 Aggregate | 预计算粗粒度，加速查询；不能替代原子粒度 |
| 合并事实 Consolidated | 把同一粒度的多个过程度量放一张表，减少跨事实 Join |
| 分配事实 Allocated | 把头表费用分摊到行，才能在行粒度算毛利 |
| 晚到事实 Late arriving | 事件晚于维表生效或晚于分区窗口到达，需要补键与回放 |

**信心：高**（基础三类、可加性、退化维、无事实）；**中**（分配/晚到等进阶手法——S2 有定义，本文未展开实现细节）。

## 8 维度表与缓慢变化维

维度是分析入口。BI 筛选和分组几乎都走维属性，所以治理成本主要砸在维表，而不是事实表（S2）。

### 8.1 高频维度技术

| 名词 | 一句话 |
|------|--------|
| 一致性维度 Conformed | 跨多个事实表共享同一含义的维，总线架构的钉子 |
| 角色扮演 Role-playing | 同一维表多次出现：下单日、发货日、签收日都指向日期维 |
| 垃圾维 Junk | 把一堆低基数标志/类型码收进一张维，避免事实表上十几个外键 |
| 迷你维 Mini-dimension | 把高频变化属性（如信用分档）拆出去，控制 SCD2 行膨胀 |
| 桥接表 Bridge | 处理多值关系：一笔订单多个销售员、一个病人多个诊断 |
| 日历日期维 | 必须物化。不要只用 SQL 日期函数替代完整日期属性 |
| 收缩上卷维 Shrunken | 聚合事实使用粗一级的一致性维，如月历相对日历 |
| 总线矩阵 Bus matrix | 行是业务过程，列是一致性维度；企业 DW 的规划图 |

### 8.2 缓慢变化维 SCD

国内常说的 **拉链表**，对应的是 Type 2 的存储形态（业务键 + 生效/失效时间；当前行失效日常用 `9999-12-31`）。S2 给出的类型：

| 类型 | 做法 | 能回答 |
|------|------|--------|
| Type 0 | 永远保留最初值 | 开户时的获客渠道 |
| Type 1 | 原地覆盖 | 只关心当前邮箱、当前地址 |
| Type 2 | 新增一行，起止日期 + 当前标志 | 当时他是不是 VIP？历史事实跟哪版维走 |
| Type 3 | 加「前值」列 | 只要最近一次变更前后对比 |
| Type 4 | 变化快的属性进迷你维 | 信用分每天变，客户主维不能每天涨一行 |
| Type 5 到 7 | Type 1 当前值与 Type 2 历史的组合 | 既要「当时」，也要「按现在的客户分层回看」 |

全量 / 增量 / 快照 描述的是 **加载方式**，和 SCD **策略正交**：可以每天全量覆盖一张 Type 1 维，也可以对 Type 2 做增量拉链。

**信心：高**（Type 0–4 与拉链对应）；**中**（Type 5–7 的具体列设计需对照 Toolkit 原文，本文只保留用途）。

## 9 键、拉链与 Data Vault 构件

事实表外键应指向仓库自己发的代理键；源系统的客户号只作为自然键保存在维表里。

| 名词 | 一句话 |
|------|--------|
| 代理键 Surrogate key | 仓库自己发的无意义整数主键。事实表外键指向它，而不是源业务键 |
| 自然键 Natural key | 源系统业务键，如客户号。会复用、会改、会跨系统撞车 |
| 持久键 Durable / supernatural | 即使自然键重编码也保持稳定的人/物身份 |
| CDC | 捕获源库变更流，给增量入仓和 Satellite 历史供料 |

不用源客户号当事实表外键的原因：源键会合并、拆分、重开。代理键把「仓库认定的同一客户」和「源系统今天的编号」拆开，SCD2 才能让历史订单钉在下单当天的那一版客户属性上（S2）。

Data Vault 三件套见上文 4.3。Information Mart 才是给人看的星型。

**信心：高。**

## 10 指标口径

模型解决「表怎么放」，指标解决「数怎么算」。国内数仓建设常把指标拆成可组装的零件（与阿里云 DataWorks「数据指标 / 原子指标、修饰词、时间周期」同一套思路，S3 检查器章节；美团侧实践另见 [meituan-data-governance-deep-dive.md](meituan-data-governance-deep-dive.md)）。

| 名词 | 一句话 | 例子 |
|------|--------|------|
| 原子指标 | 不可再拆的业务度量 + 算法 | 支付金额 = SUM(实付) |
| 时间周期 | 统计窗口 | 1 天 / 7 天 / 30 天 |
| 修饰词 | 业务限定 | 新客、APP 端、含退款 |
| 派生指标 | 原子 × 时间 × 修饰词 | 近 7 日新客 APP 支付金额 |
| 复合指标 | 派生指标再运算 | 客单价 = 支付金额 / 支付用户数 |
| 一致性口径 | 同一指标名在所有 ADS 必须同算法 | GMV 含不含取消单 |

咬合方式：原子指标落在 DWD/DWS 的可加事实列上；时间周期和修饰词来自日期维与业务维；ADS 只做最后一公里组装，不在应用层偷偷改公共口径。

**信心：中。** 「原子 / 派生 / 修饰词」是国内平台通用词汇，但各厂命名并不统一（美团配送与酒旅就不一致，见美团治理文）；不要当成 Kimball 原词。

## 11 优劣势与选用建议

| 方案 | 优势 | 劣势 |
|------|------|------|
| Kimball 星型 | 出数快、BI 友好、粒度合同清晰 | 源系统剧变时改维成本高；企业一致性靠纪律而非物理核 |
| Inmon 3NF 核 | 单一真相、集成度高 | 前置周期长；直接查询不友好，仍要派生集市 |
| Data Vault | 抗源变更、全历史、可审计 | 表数量多；不能直接当报表模型 |
| 只用宽表/ADS | 短期最快 | 口径漂移、无法复用、无法回答「当时」 |

推荐路径：

- **先要一张能分析的报表**：Kimball 原子事实 + 一致性日期/客户/商品维，落在 DWD/DIM，汇总进 DWS。
- **源系统多、监管要溯源**：集成层 Data Vault 或 3NF，Gold/ADS 仍出星型。
- **已经湖仓一体**：Bronze 贴源，Silver 清洗或 Vault，Gold 星型；不要只停在 Bronze 目录分层。

把词串成一条工作记忆：下单要进仓时，ODS 原样落地；DIM 统一客户/商品/日期（含 SCD）；DWD 按「订单行」粒度建事务事实；DWS 做用户×天汇总；ADS 出活动排行榜。跨「下单」和「退款」对比时，必须走同一套一致性维度和一致性 GMV 算法。

下一步最有效的练习：选一个真实业务过程（如下单），画出总线矩阵的一行，并写出 DWD 的粒度声明。

**信心：高**（各方法优劣势）；选用路径是综合建议，实施时仍要按组织约束裁剪。

## 12 名词速查

按设计决策分组，避免按字母表把正交概念排在一起。

- **分层**：ODS、DIM、DWD、DWS、ADS、贴源层、公共层、应用层、数据域、业务过程、数据集市、主题域、Bronze、Silver、Gold。
