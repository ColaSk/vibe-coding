# 设计模式

按变化点选一个模式并落到当前代码或设计里。模式是结构的名字，不是目标。

目录：[./catalog.md](./catalog.md)。只在候选还不确定时打开，按「变化点」检索，不要通读。

## 何时用

新功能、新模块、设计文档、重构、解耦、API 或边界、界面与组件、以及用户问「用什么模式 / 怎么设计」时使用。

两处具体需求出现之前，用直白的函数、模块或组件。第二个变体出现，或替换成本已经很高时，再引入模式。

## 步骤

1. 用一句话写变化点：什么会变，什么调用方不能变。
2. 定层级：对象与函数、模块与进程、界面与交互。三个层级不要混在一个方案里。
3. 在 [./catalog.md](./catalog.md) 里按变化点取最多三个候选。没有对上的变化点，就不要用模式。
4. 选一个。写出它多出来的类型或模块，以及因此不能再做的事。
5. 按项目里已有的语言和目录画出骨架：类型、模块边界或组件树。不新造一套命名。
6. 对照「停手条件」。碰上下面任一条，删掉模式，保留直接实现。

## 停手条件

- 只有一个实现，而且看不到第二个。
- 模式名和代码对不上。代码说了算，删掉名字。
- 为了模式增加的类型，比它消掉的分支还多。
- 用单例、服务定位器或全局事件总线掩盖依赖。依赖写在构造或参数上。
- UI 上用复杂状态机描述一个只有开和关的控件。

## 输出

设计讨论或设计文档用下面的结构。用户只要改代码时，把同一判断写进改动说明，并直接改代码。

```markdown
## 变化点
[什么会变。什么必须保持稳定。]

## 选择
[一个模式名，对应 catalog 里的变化点。]

## 形态
[类型、模块或组件。谁依赖谁。]

## 不选
[一个最接近的候选，以及不选它的原因。]

## 停手
[为什么现在值得拆；或为什么保持直接实现。]
```

## 落地

- 名字与项目现有代码一致。项目里没有的模式名，不要引进文件名。
- 对象级模式落在类型与函数上。模块级模式落在目录、接口和依赖方向上。UI 模式落在组件边界和状态归属上。
- 改完后，变化点所在的那一层可以替换；稳定的那一层不用改。
